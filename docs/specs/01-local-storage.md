# Local storage

Source idea: [Local storage](../ideas/01-local-storage.md)

## Problem Statement

Repository users need local encrypted secrets without a hosted secret manager, while sharing environment-reference configuration and keeping each user's values private. This adds key-lifecycle responsibilities that existing external providers may already handle for some users.

## Solution

Add the `local-storage` provider alongside existing providers. Keep references in the existing configuration and ciphertext in repository-local, per-key storage. Resolve values through an SSH agent and offer independent encrypted-value creation, updates, reference browsing/linking, and deletion through the TUI. Q28 of the source idea records the original agreement; this spec incorporates the subsequent user-authorized conversational changes to storage placement and TUI management. Documentation alignment does not authorize implementation or advance release approval.

## User Stories

1. As a repository user, I want encrypted local values resolved through my SSH agent, so that I can inject secrets without a hosted secret store or exporting my private key.
2. As a collaborator, I want shared environment mappings to resolve my own values with explicit identity selection when needed, so that another user's value is never silently substituted.
3. As a TUI user, I want to create, update, link, and safely remove encrypted values and references, so that I can manage repository-local secrets without plaintext command arguments.

## Implementation Decisions

### Context and ownership

The source idea's repository findings describe the historical preimplementation baseline, not the current system. See [Architecture](../ARCHITECTURE.md) for current module boundaries, selected v1 fields/byte encodings, filenames, libraries, and internal APIs. Those implementation details remain delegated within this spec's behavioral and security constraints, not a promised stable extension API. [Ticket 07](../tickets/local-storage/07-experimental-release-readiness.md) owns recorded verification evidence and outstanding release blockers; neither implementation nor documentation proves release readiness.

### Agreed provider, identity, and storage contracts

- Persist the exact, case-sensitive source name `local-storage`. Preserve existing configuration discovery and the string-valued environment-reference schema; encrypted storage is separate directly under `.psst/` beside the selected configuration, not beside the caller's working directory. Per-key JSON and lock files live at that directory's root. Do not read or automatically migrate legacy `.psst/local-storage/` files; relocation is explicit manual recovery, preserving private permissions and avoiding filename collisions.
- Store one JSON file per public key, containing separate records by local storage ID. Record identity is `(ID, public key)`; multiple environment mappings may link to it without duplicating storage. Different users may store different values for the same ID in the shared directory. Use hash-safe key filenames; IDs never become paths. Metadata remains visible, and ciphertext is suitable for committing.
- References are `secret-id` or `secret-id#SHA256:fingerprint`, using the OpenSSH SHA-256 public-key fingerprint. IDs are nonempty, case-sensitive exact strings, excluding `#` and control characters. Conservative additional ID/input limits are delegated.
- An unqualified reference resolves only when exactly one agent key matches a stored value for that ID, not merely an identity elsewhere in storage. Qualified references select that key for that entry. Missing keys or values, unresolved ambiguity, agent rejection, and decryption failures are errors; never fall back to another identity or plaintext.
- Any resolution failure from this provider stops wrapped-command launch and `.env` export, even when other entries succeed or inherited variables exist. Other providers retain their existing best-effort behavior. Copy propagates failures normally; the TUI reports per-entry errors and remains usable. Successful empty values remain valid provider results; existing consumer-specific empty-value behavior is otherwise unchanged.

### Agreed cryptography and agent boundary

- Private-key operations occur exclusively through the standard SSH-agent protocol. Never read private-key files or fetch a separate encryption key using `op`. Target Ed25519 SSH Key items held by 1Password, with 1Password as the required tested integration; allow compatible agents without vendor detection, but advertise only tested integrations.
- Use verified, repeatable deterministic Ed25519 signatures over fixed-format, domain-separated challenges to derive encryption keys with HKDF-SHA256. Encrypt in-process with AES-256-GCM, fresh random salt and nonce on every write, and a versioned envelope authenticating ID, key identity, and version metadata. Verify signatures and check signing repeatability during creation. Validate metadata and sizes before requesting signatures.
- Use maintained Rust cryptographic primitives, not custom primitives or external plugins. Precise v1 JSON fields, challenge encoding, compatible libraries, and hash-safe filenames remain implementation-owned and documented through [Architecture](../ARCHITECTURE.md), with tests within these contracts; do not treat a historical example construction as a selected dependency.
- Initially connect only through Unix `SSH_AUTH_SOCK`. Apply existing `PSST_TIMEOUT` semantics (positive seconds, default 30 for missing/invalid values) to each fetch/save agent-work phase, including queued signing time, not human editing time. Serialize signing requests. Timeout or cancellation aborts the phase without automatic retry or fallback; completed file changes follow the persistence contract below.
- Deduplicate identical `(ID,key)` fetches within an operation. Plaintext and derived keys have operation-local lifetimes only, with no persistent cache; TUI refetches start fresh operations. Discard secrets after use and apply best-effort zeroization, without promising safety against a compromised process.

### Agreed validation and persistence

- Bound each per-key file to 4 MiB. Reject malformed data, duplicates, unknown versions, mismatched key metadata, invalid field sizes, and authentication failures. Refuse symlinked storage paths and use private local permissions. Strict validation must precede signing where applicable.
- Per-key saves and encrypted-record removals use the same validated loaded snapshots, private-path checks, locking, loaded-content conflict detection, and atomic replacement; never silently overwrite concurrent same-key edits. Preserve unrelated IDs and other users' per-key files; retain the per-key file when its last record is removed.
- Encrypted-value creation persists storage independently and returns to the browser without saving configuration or requiring an environment name. Linking the resulting reference saves configuration separately, so encrypted creation persists storage before its new mapping. When deleting an environment mapping with optional ciphertext removal, persist configuration before removing ciphertext. Independent browser deletion removes ciphertext without writing configuration. There is no cross-file transaction promise. Failed reference creation may leave unused ciphertext; failed storage deletion leaves ciphertext. Report partial completion accurately, including failures after replacement, rather than claiming rollback or complete success. The mapping-deletion ordering prefers unused encrypted records over dangling references; independent browser deletion deliberately keeps mappings after explicit confirmation.

### Agreed TUI management

- Use unified controls across the app: dashboard and browser lists filter immediately as ordinary characters are typed, without a separate `/` search mode. `Backspace` erases filter text only and never deletes a record or navigates upward. Use arrow keys for list navigation; legacy `/`, `q`, `c`, `a`, `e`, `j`, `k`, Space, and `?` actions are removed rather than competing with filter input. In lists these printable characters are filter text, not commands.
- `Ctrl+D` requests deletion of the selected dashboard entry or exact qualified ciphertext record in the Local storage IDs browser; it is inert on creation rows, empty results, and loading states. `Ctrl+N` starts the applicable new-entry/value flow; `Enter` edits an entry or selects a browser row. `Ctrl+B` opens supported provider browsing from the entry editor; `Ctrl+S` saves the active editor; `Ctrl+C` quits from every view; `F1` opens help. Help and visible hints must describe these controls consistently, without competing legacy shortcuts or `Ctrl+P` preview.
- `Ctrl+R` reveals or hides with automatic remasking after 30 seconds. Dashboard entries, reference editors, and selected browser references resolve on demand, including executing a shell provider only when explicitly requested. Manual-value and encrypted-value editors reveal only the typed draft, never fetch, execute, or decrypt an existing value. `Ctrl+Y` copies the corresponding secret or typed draft; reference resolution is on demand when needed. Browser listing and reference selection remain metadata-only until an explicit reveal or copy request.
- `Esc` is the dashboard's primary exit and quits immediately regardless of filter text, without clearing the filter first. In a browser, `Esc` clears a nonempty filter first; with an empty filter it goes to the browser's parent level and then back to the entry editor at the root. `Esc` in an editor discards its unfinished draft and returns to its parent; it never undoes completed writes. Confirmation dialogs retain their explicit confirm/cancel controls below.
- The main list has a selectable **+ New entry** row: `Enter` on that row and `Ctrl+N` both start an entry draft. Both the ordinary entry editor and encrypted-value editor label the reference/ID field **Local storage ID**; the browser title is **Local storage IDs**. `Ctrl+B` opens the provider's in-TUI browser, listing all validated stored IDs and public-key fingerprints, including unlinked records and keys absent from the agent. Browsing requires no agent access, signing, or decryption.
- `Enter` on a stored record selects its qualified `ID#SHA256:fingerprint` reference; save the environment mapping separately with `Ctrl+S` in the ordinary editor. Linking is direct selection of an existing reference, without signing, decryption, or ciphertext rewriting. Remove the separate `Ctrl+U` reuse action.
- The browser has a selectable **+ New value** row: `Enter` on that row and `Ctrl+N` both open independent encrypted-value creation. Both creation rows show their label without redundant “Enter / Ctrl+N to create” text. Collect ID, exact value, and key selection, not an environment name. Creation auto-selects only a sole eligible agent key; otherwise offer a fingerprint chooser. Creation-generated references omit the selector only when unambiguous under the resolution rule; browser selections always remain qualified. A supplied qualified reference must match the selected key.
- Value drafts start empty, not from cached or decrypted existing ciphertext. Preserve exact UTF-8 text, including empty and multiline values; `Enter` in the value field inserts a newline, and bracketed paste preserves whitespace. Reject NUL, including the entire offending paste, rather than silently changing input. Drafts are masked by default and follow the draft-only reveal contract above.
- `Ctrl+S` saves encrypted storage, confirming replacement of an existing `(ID,key)` record and warning that updates affect all references to it. Declining replacement retains the draft. Update through the browser's creation flow using the existing ID/key and replacement text. Never log plaintext or place it in argv. Report full errors and partial outcomes in a scrollable details panel.
- Discarded drafts are zeroized. Cancellation and stale results must never link an old draft's reference into a new draft or delete a cancelled mapping. Reopening after external configuration edits reloads the relevant snapshots; unused records are not automatically cleaned up.
- In the Local storage IDs browser, `Ctrl+D` on a selected existing qualified ID/key row opens confirmation for that exact `(ID,key)` record. `Enter` or `y` confirms encrypted-record removal; `Esc` or `n` cancels without changes. Warn that configuration mappings are kept and references to the removed record will fail; a possible shared-reference count may cover only the loaded configuration, with other configurations explicitly unknown. Removal requires no SSH-agent access, signing, or decryption and works for unlinked records and keys unavailable from the agent. Configuration bytes and the entry draft remain unchanged on success, cancellation, or failure. Failures before replacement keep ciphertext; failures after replacement report that the record was removed with uncertain storage durability, never rollback.
- When deleting an environment mapping, ask whether to delete its encrypted record too, defaulting to keeping ciphertext; `Tab`, not Space, toggles that option. `Enter` or `y` confirms; `Esc` or `n` cancels. Warn about known shared references in the loaded configuration without claiming repository-wide reference discovery. Delete only an explicitly selected or unambiguously resolved record, never all users' values for an ID; keep ciphertext when identity is unresolved.

## Testing Decisions

### Existing seams and proposed additions

At spec creation, existing binary-level CLI tests use isolated configurations, fake executables, observable subprocess behavior, and filesystem assertions. PTY tests exercise real TUI keystrokes, rendered output, persistence, and terminal restoration; UI tests also use Ratatui's TestBackend for masking, cancellation, and stale-result behavior. Shared provider dispatch, configuration persistence, and dotenv conversion already have focused tests.

**Proposed testing approach:** reuse CLI and PTY boundaries for end-to-end behavior, backed by one shared deterministic fake SSH agent on a temporary Unix socket. Extend test fixtures to set that socket explicitly and prevent normal tests from inheriting personal-agent access. Retain focused crypto/format, provider-operation, persistence, and UI tests where the agreed lower-level coverage cannot be reliably established through those two high-level boundaries. Operation contexts and fault-injection facilities are internal implementation/testing seams, not new user-approved interfaces; current interfaces are documented through Architecture.

### Acceptance coverage

- **CLI/provider boundary:** verify exact reference parsing and ID rules; per-ID zero/one/multiple identity matches; explicit selection with multiple loaded keys; absent keys/records; unsupported keys; agent refusal/disconnection; malformed responses; and successful exact-text decryption. Exercise shared mappings and per-user records, config-relative direct `.psst/` storage from another caller directory, no reads or automatic migration from legacy storage, and unchanged legacy configuration/provider behavior.
- **Fail-stop and consumers:** on each provider-resolution failure class, prove the wrapped command never runs and `.env` is neither created nor replaced, including inherited-variable and mixed-success cases. Verify successful injection/export, empty/multiline handling through existing consumer rules, and copy failure without clipboard-helper execution. Retain other providers' warning/omission policy, passthrough arguments, order, and concurrency regressions.
- **Agent/operation boundary:** count requests to verify deduplication, serialized signing, and fresh TUI refetches without cross-operation caching. Use controllable queued/delayed responses to verify deadline inclusion of queue time, cancellation of active/queued work, no retries/fallback, and usable subsequent operations. Verify no private-key-file access or `op` invocation.
- **Crypto/format boundary:** round-trip empty, multiline, whitespace, Unicode, and boundary-size values; reject NUL. Verify fresh salt/nonce on repeated writes, deterministic verified signatures, and failure on nonrepeatable or invalid signatures. Alter ciphertext, authentication tags, ID/key/version metadata, and envelope sizes to prove rejection. Reject malformed/duplicate/unknown-version records, key/path mismatch, files above 4 MiB, and symlinked storage paths; demonstrate that pre-sign validation failures produce no signing requests. Check documented v1 encoding with stable test fixtures or vectors and selected-library compatibility/security checks.
- **Persistence boundary:** verify private permissions, whole-file atomicity, preservation of other IDs/users, lock contention, and loaded-content conflicts. Inject failures at both stages of creation/deletion and at replacement/sync boundaries; assert ordering, actual surviving artifacts, accurate partial-completion reports, and no silent clobbering. No test should imply cross-file atomic rollback.
- **Unified-controls boundary:** use focused UI cases and representative PTY workflows across dashboard, browser, reference editor, manual editor, and encrypted-value editor. Verify immediate filtering (including former shortcut letters, `/`, Space, and `?`), Backspace at nonempty/empty filters without deletion or upward navigation, arrow navigation, creation rows, and browser filter-first Esc followed by parent navigation, editor discard, and dashboard Esc exit with or without filter text. Exercise the applicable Ctrl+D/N/R/Y/B/S/C, Enter, and F1 actions and matching help/hints; prove legacy letter actions and Ctrl+P preview are absent. Verify on-demand reveal/copy resolution and errors, manual/encrypted draft-only behavior with no provider requests, reveal/hide and 30-second expiry, and no unintended fetch from listing or selection. Verify Tab toggles optional ciphertext removal while Space does not. Treat this as required coverage, not evidence of completed implementation.
- **TUI boundary:** exercise both selectable new rows with `Enter` and `Ctrl+N`, the Local storage ID label, `Ctrl+B` browsing across all stored keys/IDs without agent access or decryption, qualified browser selections, and direct linking without signing or a `Ctrl+U` action. Verify independent creation without an environment name returns to browsing with configuration unchanged, followed by separate mapping save. Exercise key selection, record updates, creation-selector authoring, replacement/shared-reference warnings, and masked exact-text editing with empty/multiline/paste/NUL cases, draft-only `Ctrl+R` reveal/hide, and 30-second remasking matching manual values. Exercise default-keep mapping deletion, explicit deletion, unresolved identity, known shared references, and preservation of other users' records. Cover browser deletion confirmation/cancellation, unlinked and agent-unavailable records without agent requests, mapping-kept warnings and loaded-only possible-reference counts, unchanged configuration bytes and entry drafts, inert new/empty/loading states, and Backspace filtering. Verify snapshot/path/lock/conflict protections, unrelated-record preservation, last-record empty-file retention, and accurate pre-/postreplacement outcomes for independent deletion. Cover per-entry errors, cancellation, stale results, fresh refetches, no unintended plaintext rendering/logging/argv, and terminal restoration. Use focused UI tests for exhaustive states and PTY tests for representative complete workflows.

### Release gates

- Require the automated fake-agent, crypto/format, persistence, TUI, and fail-stop regressions above, plus existing formatting, Clippy, tests, and release builds on Linux/macOS x86_64 and ARM64 targets. Verify Rust 1.88 and selected dependencies explicitly; stable CI alone does not establish minimum-version compatibility.
- Require consented, opt-in real 1Password end-to-end checks on Linux and macOS covering creation, subsequent decrypt/update, agent approval/rejection, and repeatability. Normal CI must never contact personal agents or keys. Record tested integrations rather than assuming socket identity proves 1Password custody.
- Require setup, format, recovery/manual-migration, and security documentation explaining the threat boundary and accepted limitations below. Mark the feature experimental until independent crypto/format review establishes the production-readiness gate.
- These are required gates, not claims of completed verification. [Ticket 07](../tickets/local-storage/07-experimental-release-readiness.md) records partial implementation evidence and unmet gates; experimental labeling does not waive them. The source idea records only a user-authorized toy signature/crypto round-trip and modified-tag rejection; that did not validate a production format, prove 1Password integration, or constitute independent review.

## Out of Scope

- Noninteractive storage-management commands, bare management subcommands, standalone store browser outside the entry editor's provider browser, import/export management, and automated orphan cleanup. Existing runtime `.env` export remains supported; it is not storage export management.
- Automatic migration/rotation, recovery recipients, and multi-recipient shared-secret distribution.
- Key types beyond deterministic Ed25519, private-key-file access, separate encryption keys fetched with `op`, custom cryptographic primitives, and external encryption plugins.
- Agent autodiscovery/startup, automatic retries, Windows agent support, and guaranteed forwarded-agent detection.
- Metadata hiding and replay/rollback protection against valid repository history.
- Changes to other providers' failure policy or replacement of existing configuration discovery/schema.

## Further Notes

- Agent signing authorization grants durable decryption capability: an authorized process can retain signatures/derived keys after the agent locks. Agent-only custody does not keep derived keys out of psst memory. Warn against untrusted agent forwarding and recommend per-operation confirmation; actual approval frequency depends on agent settings.
- Recovery depends on preserving the SSH key in 1Password. Losing it loses decryptability. Manually migrate while the old key works by creating new `(ID,key)` records and updating explicit selectors as needed. Rotation cannot revoke old Git history or captured derived keys.
- Editor layout beyond the specified controls and additional conservative input limits remain delegated alongside implementation format/library details. Current provider/editor interfaces are architecture-owned, not settled as stable APIs by this spec.
- The source idea retains the original Q17 nested-directory choice and Q27 browser exclusion; subsequent user-authorized changes select direct `.psst/` storage and the integrated provider browser described here, without adding a standalone management application. Completed tickets retain their originally accepted scope and verification provenance, explicitly marked historical where superseded. Ticket 07 inventories the current workflows separately from historical verification. Documentation alignment does not upgrade those approvals or statuses.
