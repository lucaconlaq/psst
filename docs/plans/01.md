# Plan 01: Per-user encrypted local provider

Status: design proposal; encryption backend feasibility must be resolved before
implementation. No provider implementation is included in this plan.

## Goal and agreed behavior

Add a provider whose per-user secrets live in `.psst/`, beside the selected
config file. This applies equally to `psst.json`, `.psst.json`, and any config
selected through `PSST_CONFIG`. Reuse existing config discovery; do not search
separately for the encrypted store or anchor it to the invocation directory.

- Config shares secret identifiers, not secret values. Alice and Bob can each
  have a different value for `ABC_API_KEY` using the same config reference.
- Each user has a separate encrypted collection and published public key. These
  files coexist in Git; a user's collection is encrypted only for that user's
  selected identity, never for other published keys.
- Keys come from `ssh-agent`; the initial target is an Ed25519 key held in
  1Password and exposed through its SSH agent.
- Secrets are added, edited, read, and deleted through the existing TUI workflow.
- Reads and saves interact only with the selected user's encrypted collection;
  plaintext values must never be persisted in the config.
- There are no recipient approvals, shared-recipient lists, or access-granting
  re-encryption workflows. Publishing another key does not affect existing users.
- Git synchronization remains the user's responsibility; psst does not commit,
  push, or pull.

## Proposed layout

```text
project/
├── psst.json
└── .psst/
    ├── <alice-fingerprint>.pub
    ├── <alice-fingerprint>.enc
    ├── <bob-fingerprint>.pub
    └── <bob-fingerprint>.enc
```

Use one encrypted collection per identity, not one shared collection or a
separate ciphertext for every secret. Public keys and ciphertext are directly
in `.psst/`. A fingerprint identifies a cryptographic identity, not a username;
one person may have multiple identities.

The filename fingerprint should be a filesystem-safe encoding of the SSH SHA-256
fingerprint, calculated from the key blob, not the comment. Display conventional
`SHA256:...` fingerprints in the interface. Validate filename/key agreement for
the selected identity and reject malformed or unsupported selected key files.
Never use comments, OS usernames, or Git author names to select a collection.

Commit public keys and ciphertext. Never store private SSH keys or plaintext
secret files. Any auxiliary enrollment material required by the backend must be
documented before finalizing this layout, including whether it is committed or
local-only. `.enc` intentionally avoids promising a specific encryption format.

Proposed provider ID: `encrypted` (not yet explicitly confirmed).

```json
{
  "ABC_API_KEY": {
    "source": "encrypted",
    "value": "ABC_API_KEY"
  }
}
```

The config value is a secret identifier, not secret content, a user fingerprint,
or an arbitrary path. Resolution selects the acting identity's collection and
then looks up that identifier. Inside each encrypted payload, use a versioned
collection of string-valued secrets. Preserve empty strings; reject duplicate
identifiers and NUL bytes. Bind the payload to its owning identity and validate
that binding on read.

## Identity selection and isolation

Select one explicit acting identity for each operation and keep that selection
consistent across all encrypted references, including parallel fetches.

- If exactly one eligible identity is available, select it automatically.
- If multiple identities are eligible, the TUI offers an explicit selection.
  Define an explicit selector for command execution/export before implementation;
  ambiguous noninteractive operations must fail rather than guess.
- First-time enrollment must allow selection of a supported agent identity even
  when it has no published key or collection yet.
- Display the acting fingerprint in the TUI so users know whose values they edit.
- A missing collection or identifier is an actionable error on fetch. Never fall
  back to another user's value or silently initialize a store during a read.
- The TUI may explicitly create the selected user's collection or add their
  missing values. Other users' collections are not prerequisites for doing so.
- Never merge collections from multiple identities. Changing the acting identity
  clears decrypted state and unsaved edits, with confirmation if needed.
- Unrelated users' files are not decrypted or rewritten. Define how unrelated
  malformed files are reported without blocking valid selected-user operations.

Do not persist machine-specific identity selection in the shared config. The
selector mechanism and any local preference storage remain to be specified.

## Encryption feasibility: first milestone and release blocker

Ordinary age SSH Ed25519 support is not sufficient for the intended 1Password
workflow: decryption normally needs private-key material, while an SSH agent
exposes signing operations, not arbitrary decryption or Ed25519 private-key
export. Do not assume an age SSH recipient can be decrypted through 1Password's
agent, and do not require private-key export as a silent workaround.

Before building the provider:

1. Evaluate maintained, reviewed agent-compatible encryption integrations.
2. Demonstrate enrollment, encryption, and decryption with a real 1Password
   Ed25519 identity, without exporting its private key.
3. Document enrollment material, identity binding, authenticated encryption,
   recovery requirements, and whether auxiliary files are local or committed.
4. Validate Linux/macOS support, Rust 1.88 compatibility, prompts, cancellation,
   dependency maintenance, and the security assumptions of any signing-based
   key derivation, including signature reproducibility and domain separation.
5. Demonstrate that another user's identity cannot decrypt the collection.

Unlike the previous shared-secret proposal, encryption by other users while the
owner's agent is offline is not required. Only the owner needs to encrypt and
read their values. This changes backend requirements but does not make arbitrary
signature-derived encryption safe. Use established cryptography; do not invent
an agent-signing scheme.

If no suitable backend exists, return to the user with explicit alternatives,
such as an additional encryption identity protected/unlocked using the SSH
agent, or changing the identity requirement. The layout remains tentative until
this milestone succeeds.

## Key publishing command

Proposed name: `psst add-key`, clearer than `add-pkey` and distinct from adding a
secret. This name is not yet confirmed.

- Discover the selected config and create its sibling `.psst/` only on publish.
- Connect through `SSH_AUTH_SOCK` and list supported identities.
- Show fingerprints and sanitized comments; let the user select one key.
- Publish its canonical public key atomically under its fingerprint filename.
- Publishing an already identical key is idempotent. Do not overwrite a
  conflicting file.
- Complete any backend-required enrollment while the selected agent is present.
- Explain which files must be committed and that the key identifies this user's
  private collection, not a request for access to another user's secrets.
- Do not decrypt or rewrite existing collections just to publish a key.

The current CLI treats positional words as a wrapped executable. Reserving
`add-key` must preserve `psst -- add-key ...` as an explicit executable escape
and preserve existing argument passthrough and flag precedence.

## Access and Git workflow

1. Alice publishes her key and creates her encrypted collection through the TUI.
2. Alice commits her public key, ciphertext, and config references.
3. Bob clones and publishes his own key. The shared config already contains the
   identifiers, but Bob's values do not exist yet.
4. Bob enters his own values through the TUI and commits his key and ciphertext.
5. Alice and Bob pull normally. Each resolves the same config identifiers using
   only their own collection and updates only their own ciphertext.

Neither user needs the other's approval, agent, or plaintext. A new shared
identifier does not imply every user's collection already has a value for it;
missing values must be reported clearly and entered independently.

## TUI and provider integration

The current `Provider` interface supports fetching, labels, masking, and optional
browsing; it has no secret-write API. This feature needs more than registration
of a fetch-only provider.

- Implement fetching in `src/providers/encrypted.rs` and register it centrally.
- Add generic optional managed-secret capabilities rather than provider-specific
  dispatch in `src/ui.rs`. Define loading, saving, deletion, and identity context
  as part of the design before implementation.
- Separate the persistent reference field from the masked, transient secret-value
  editor. `sensitive_reference()` alone does not solve this distinction.
- Keep reveal, copy, command execution, and `.env` export on shared fetch paths.
- Preserve opt-in reveal; keep decrypted values and payload buffers zeroizing
  where practical, and clear them on cancellation or editor expiry.
- Editing one secret preserves all other secrets in the acting user's collection,
  including unreferenced ones. Never modify other users' collections.
- Distinguish editing a shared config reference from editing a personal value.
  Reference changes affect everyone; value changes affect only the acting user.
- Proposed deletion behavior: explicitly confirm removing the acting user's
  stored value and avoid deleting it while other config entries reference it.
  Removing only a reference or switching providers must not silently destroy
  stored values. Never delete other users' values as part of this operation.

There is no recipient approval prompt or shortcut. Identity selection is not
recipient approval. Key rotation/recovery is a separate future design concern;
publishing a replacement key must not automatically migrate old ciphertext.

## Persistence and failure handling

- Bound ciphertext size, decrypted payload size, key count, and agent responses.
- Validate schema without including secret values in errors or logs.
- Reject unexpected symlinks/non-regular selected key and ciphertext files;
  constrain store access to the selected directory.
- Use cooperative locking, baseline conflict detection, and atomic replacement
  to prevent lost updates. Git pull/edit races must be detected, not overwritten.
  Scope collection conflicts per identity; coordinate shared config changes too.
- Never stage plaintext in temporary files; only ciphertext may be written.
- Use restrictive local directory/file permissions and safe atomic-write helpers.
- Adding a config reference and replacing ciphertext is a multi-file operation:
  design recovery and ordering explicitly, since two renames are not a single
  transaction. Do not report success after a partial save. Prefer an orphaned
  encrypted value to a reference whose value was never persisted.
- Missing agent, denied authentication, ambiguous identity, malformed selected
  key, corrupt ciphertext, and missing identifiers produce actionable,
  secret-free errors. A failed read must never initialize or overwrite a store.
- Reads do not re-encrypt automatically. Writes require the selected owner's
  identity and encrypt only for that identity.
- Reuse one short-lived decrypted collection per operation where practical,
  avoiding one agent prompt per secret during parallel fetches. Scope caching
  to the selected identity, store revision, and operation; do not keep unlocked
  secrets indefinitely. Avoid concurrent authentication prompts and stop on
  explicit user cancellation.

## Security expectations

Each collection contains only its owner's values. Publishing keys together in
Git does not grant cross-user access. Users with access to the repository can
see public keys, ciphertext, shared identifiers, and ciphertext history, but
must not be able to decrypt another user's collection with their own identity.

Encryption does not necessarily authenticate the writer. Anyone able to modify
the repository can replace files; v1 relies on trusted repository changes, not
cryptographic writer identity. Document backend-specific tamper detection and
rollback limitations; authenticated encryption alone does not prevent replay of
older valid ciphertext.

Deleting or rotating a key cannot revoke decrypted secrets or ciphertext retained
in Git history. Rotate actual credentials when a key is compromised. Encryption
does not protect secrets after reveal, clipboard copy, environment injection,
or `.env` export. Loss of the owner's identity and any required enrollment
material means loss of access; there is no server-side recovery.

## Implementation sequence and acceptance tests

1. Resolve the backend blocker and document the final format/enrollment model.
2. Specify identity selection, owner binding, local preferences, and failure
   behavior for missing personal values.
3. Implement per-identity store validation, encryption/decryption, atomic updates,
   and conflict handling with generated test identities and a fake agent.
4. Implement key publishing and CLI parsing tests.
5. Register fetching and generic managed-secret TUI capabilities.
6. Add personal-value editing, identity selection, and coordinated config/store
   saving without recipient approvals or cross-user rewrites.
7. Update README and provider documentation with Git and recovery workflows.

Tests must cover config-relative placement (including `PSST_CONFIG` and ancestor
discovery), filename/key mismatch, malformed selected keys, multiple identities,
missing/denied agent, explicit cancellation, and wrong-identity decryption failure.
Verify Alice and Bob resolve `ABC_API_KEY` to different values using identical
config references, and that editing either collection leaves the other's bytes
unchanged. Publishing another user's key must not change encryption recipients
or trigger approval prompts. Missing personal values must never fall back to
another collection. Cover the chosen handling of malformed unrelated files.

Cover first-user and subsequent-user enrollment, empty-string values, unreferenced
value preservation, shared-reference versus personal-value deletion, identity
switching, masking, reveal, export, parallel fetch prompt coordination, corruption,
NUL/size limits, concurrent edits, and partial-save recovery. Assert no secret
literals appear in config, logs, errors, or disk staging files. Keep normal tests
independent of real 1Password accounts; perform the targeted 1Password
interoperability check separately.

## Remaining confirmations

- Final command name (`add-key` proposed) and provider ID (`encrypted` proposed).
- Explicit identity selector for command execution/export and local preference
  behavior, including eligibility when several agent keys are present.
- TUI deletion semantics for shared references versus personal stored values.
- Acceptable enrollment/layout changes if required for 1Password agent support.
- Key rotation, recovery, and treatment of unrelated malformed store files.
