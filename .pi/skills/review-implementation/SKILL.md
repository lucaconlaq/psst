---
name: review-implementation
description: Check whether code correctly implements a spec or ticket. Use for implementation and acceptance-criteria reviews. Default to edited files and report only; confirm any user-defined file selection and an explicit request to fix findings immediately.
---

Default to files with staged, unstaged, or non-ignored untracked changes without asking for confirmation. If there are no edits in the default scope, say so and stop. Accept any user-defined selection, not just a file, folder, whole project, or commit. For a non-default selection, resolve it to a concrete scope and use `ask_user_question` to confirm that scope before reviewing; stop if confirmation is declined or cancelled. Exception: when invoked by the `implement` skill, its supplied scope and immediate fixes are preauthorized; announce the resolved scope and apply corrections without confirmation.

First, inventory the selected scope and print a checklist of every file to review, including deleted paths. Identify excluded generated outputs, caches, and vendored code separately. Keep the checklist updated as each file is reviewed; review every listed file fully, never silently skip one, and do not claim completion while any remain unchecked. If blocked or interrupted, report checked/total counts and the remaining paths.

Read applicable `AGENTS.md` instructions, `docs/rules/index.md`, and matching rules before reviewing. Repository paths are relative to the repository root, not this skill directory. Read the supplied or clearly matching spec or ticket and its linked requirements; use `docs/GLOSSARY.md` for domain terms and `docs/ARCHITECTURE.md` for module boundaries. Beyond scope confirmation, ask only if the requirement document is missing or ambiguous, or requirements conflict; do not invent acceptance criteria.

Announce the scope and requirement document paths. Trace each relevant requirement through the implementation and tests, checking missing behavior, edge cases, error paths, and regressions. Check for scope creep: added behavior or unrelated changes not requested by the spec or ticket. Distinguish necessary implementation support from extra features; cite the agreed scope and evidence for each finding, and flag ambiguity rather than assuming unmentioned details are forbidden. Read full files and relevant diffs; distinguish staged and unstaged changes, and account for additions, deletions, and renames. Follow callers and dependencies as supporting context without silently expanding scope. For edits or a commit, distinguish introduced defects from pre-existing gaps.

Run relevant non-mutating tests with the documented toolchain when safe; passing tests alone do not prove implementation correctness. Report actionable findings by severity with `path:line`, the spec or ticket requirement, evidence, and a concise proposed correction. Summarize requirements as satisfied, missing, or unverified, along with checks and coverage limits. If none were found, say "No implementation issues found in the reviewed scope."

Review only by default: do not modify files or Git staging. If the user explicitly requests immediate fixes, apply confirmed corrections and necessary regression tests without another confirmation, preserve unrelated edits, and rerun relevant checks. Do not rewrite requirements to fit the code. For a historical commit, do not check it out or overwrite current work; ask if the fix target is unclear. Report fixes and remaining findings; never commit or push unless separately requested.
